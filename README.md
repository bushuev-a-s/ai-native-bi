# AI-Native BI Agent — первый тестовый вариант (прототип)

Локальная платформа: загружаешь сырые CSV → общаешься с агентом на естественном языке →
получаешь описание данных, ответы, графики и дашборды. Без облаков, всё open source.

## Быстрый старт

```bash
docker compose up -d db ollama
docker compose exec ollama ollama pull qwen2.5:7b-instruct   # один раз; модель можно сменить в .env
docker compose up --build app                                # http://localhost:8501
```

### Своя модель

Провайдер и модель задаются переменными окружения (см. `.env.example`), код менять не нужно:
- `LLM_PROVIDER=ollama`, `LLM_BASE_URL=http://localhost:11434`, `LLM_MODEL=<имя>`
- `LLM_PROVIDER=openai` — любой OpenAI-совместимый сервер (vLLM, LM Studio, llama.cpp):
  `LLM_BASE_URL=http://localhost:8000/v1`, `LLM_MODEL=<имя>`

Менторы сообщили, что при проверке подключат свои open source модели (до 80B), поэтому промпты нужно
тестировать на слабой модели.

## Архитектура

```
CSV ──► loader (кодировка, разделитель, даты) ──► PostgreSQL (сырые таблицы как есть)
                                                     │
                       profiler (типы, пропуски, топ-значения, период, дубликаты, связи по id)
                                                     │  «память о данных» → в промпт
вопрос ─► router ─► overview / explain / query / rechart / dashboard / clarify / reject
                      query: LLM → SQL → safety (только SELECT, READ ONLY, timeout, LIMIT)
                             └─ ошибка? → LLM видит ошибку и исправляет (до 2 раз)
                             → ответ простым языком + авто-график (+ SQL под спойлером)
```

| Файл | Что делает |
|---|---|
| `core/loader.py` | загрузка произвольного CSV, автоопределение формата |
| `core/profiler.py` | профиль таблиц, поиск связей, текст схемы для LLM |
| `core/agent.py` | маршрутизация, text-to-SQL с самоисправлением, графики, дашборды, контекст сессии |
| `core/safety.py` | валидатор SQL (один SELECT, чёрный список, служебные таблицы закрыты) |
| `core/charts.py` | авто-выбор типа графика и его построение (Plotly) |
| `core/prompts.py` | все промпты в одном месте |
| `core/db.py` | PostgreSQL, транзакции READ ONLY, хранение дашбордов в `_bi_dashboards` |
| `core/history.py` | история диалогов: чаты и сообщения в `_bi_chats` / `_bi_messages`, восстановление контекста агента |
| `app.py` | чат + список чатов в боковой панели + вкладка «Дашборды» (Streamlit) |

## История диалогов

Каждый чат хранится в PostgreSQL (`_bi_chats`, `_bi_messages`): роль, текст, SQL, спецификация графика,
id дашборда, время. Таблицы результатов **не хранятся** — при открытии чата они пересчитываются по сохранённому
SQL, поэтому данные в старых чатах всегда актуальны. Если пересчитать не удалось (таблицу удалили),
сообщение остаётся с пометкой. При открытии чата агенту возвращается последний результат, так что
«покажи то же самое в другом виде» работает и в старом диалоге. Название чата берётся из первого вопроса.
Пустые чаты в БД не создаются: чат появляется с первым вопросом. Служебные таблицы закрыты для SQL агента
(префикс `_bi_`). Чаты общие для всех, кто открыл приложение: привязки к пользователю пока нет.

## Что проверено, а что нет

Проверено тестами (`tests/test_core.py`, 10 тестов; `tests/test_history.py`, 11 тестов; на SQLite и заглушке LLM): загрузка CSV с разными форматами,
профиль и поиск связей, защита SQL, логика агента (роутер, самоисправление SQL, контекст, дашборды).

**Не запускалось** в окружении разработки (не было сети): Streamlit-интерфейс, реальный PostgreSQL, реальная модель.
Первый запуск у вас может вскрыть мелкие ошибки — несите их в чат, поправим. Качество text-to-SQL зависит от модели:
на 7B иногда будут ошибки, самоисправление это смягчает; при наличии GPU попробуйте модель побольше (`OLLAMA_MODEL`).

## Известные ограничения

- Файлы от `FAST_LOAD_MIN_MB` (по умолчанию 50 МБ) грузятся потоково через `COPY`, меньшие — через pandas. Порог ориентировочный: замеры на `01_Продажи` (500 000 строк, 180 МБ) ещё не сделаны (задача M3). Лимит загрузки в интерфейсе — 1 ГБ (`.streamlit/config.toml`).
- Десятичная запятая (`1,5`) и экзотические форматы дат не распознаются автоматически.
- Профиль считается по выборке (до 100 000 строк на таблицу), число строк — точное.
- Дашборд-виджеты строятся по SQL от LLM; при смене данных SQL перезапускается, но спецификация не пересоздаётся.

## Куда развивать (по приоритету)

1. Прогнать на реальном датасете кейса, собрать «золотой набор» вопросов и мерить точность SQL.
2. Аналитические инструменты на Python для сценариев 3+: сезонность, корреляции/лаги, сегментация, прогноз
   (считает код, LLM только интерпретирует — меньше галлюцинаций).
3. ClickHouse как второй бэкенд (`Database` с тем же интерфейсом).
4. Семантический слой: LLM описывает смысл каждой колонки один раз при загрузке и кеширует.
5. Редактирование дашбордов в чате («добавь виджет…», «убери…»).
