# Архитектура

Документ описывает, как платформа устроена сейчас (разделы 1–9) и какой мы видим «идеальную» версию (раздел 10, не реализовано).

## 1. Принципы

1. **Факты считает код, пересказывает модель.** Числа, период, число строк, связи между таблицами вычисляются кодом и SQL; модель только формулирует вопросы к данным (SQL) и объясняет результат простым языком. Так меньше выдуманных чисел.
2. **Данные не трогаем.** Агенту доступен один `SELECT` на запрос, в транзакции `READ ONLY`. Загрузка и предобработка идут внутри платформы, а не заранее.
3. **Слабая модель тоже должна работать.** Промпты проверялись на 7B-модели; всё, что можно решить правилами (намерение, тип графика, простые вопросы), решается без вызова модели.
4. **Всё локально.** PostgreSQL, модель и приложение в Docker; после установки интернет не нужен.
5. **Скорость важна.** Типичный вопрос стоит два вызова модели (SQL и пересказ): намерение определяют правила, а одиночные значения пересказываются шаблоном.

## 2. Общая схема

```
                        ┌──────────────────────────────────────────────┐
  Браузер  ◄──────────► │  Streamlit-приложение (app.py)               │
  (чат, графики,        │  чат · список чатов · вкладка «Дашборды»     │
   дашборды, загрузка)  │  загрузка CSV · выбор разделителя · удаление │
                        └───────────────┬──────────────────────────────┘
                                        │
        ┌───────────────────────────────▼────────────────────────────────┐
        │                      Ядро (core/)                              │
        │                                                                │
        │  loader ──► profiler ──► «память о данных» (схема, связи)      │
        │                                   │                            │
        │  вопрос ─► agent: правила маршрутизации                        │
        │             ├─ overview / explain                              │
        │             ├─ query      text-to-SQL ─► safety ─► выполнение  │
        │             │             └ ошибка → модель исправляет (≤ 2)   │
        │             ├─ rechart    тот же результат другим графиком     │
        │             ├─ dashboard  набор виджетов, параллельный счёт    │
        │             └─ clarify / reject                                │
        │                                                                │
        │  charts (Plotly) · history (чаты) · cache (виджеты дашборда)   │
        └────────────┬───────────────────────────────┬───────────────────┘
                     │ SQL (READ ONLY)               │ HTTP (OpenAI-совместимый
                     ▼                               ▼  или родной API Ollama)
            ┌─────────────────┐            ┌───────────────────────┐
            │  PostgreSQL 16  │            │  Сервер модели        │
            │  таблицы данных │            │  Ollama + Qwen2.5 7B  │
            │  _bi_dashboards │            │  (или любой другой    │
            │  _bi_chats      │            │   OpenAI-совместимый) │
            │  _bi_messages   │            └───────────────────────┘
            └─────────────────┘
```

Все три части (приложение, база, модель) поднимаются через `docker-compose.yml`. Модель можно заменить внешним сервером настройками `LLM_*`, а базу своей PostgreSQL через `DATABASE_URL`.

## 3. Компоненты

| Модуль | Ответственность | Важные решения |
|---|---|---|
| `app.py` | интерфейс Streamlit: чат, список чатов, дашборды, загрузка CSV, удаление таблиц и дашбордов | состояние сессии в `st.session_state`; сообщения сохраняются в БД сразу, поэтому не теряются при сбое |
| `core/loader.py` | чтение произвольного CSV и загрузка в БД | автоопределение кодировки (в том числе cp1251), разделителя (по ровности числа полей в строках, с учётом кавычек), дат и десятичной запятой; файлы от `FAST_LOAD_MIN_MB` идут потоково через `COPY`; при ошибке загрузка откатывается |
| `core/profiler.py` | профиль таблиц: типы, пропуски, топ-значения, период, дубликаты; поиск связей между таблицами | профиль считается по выборке (`PROFILE_SAMPLE_ROWS`), число строк точное; связи ищутся по пересечению значений идентификаторов, без ложных совпадений по общим именам вроде `id` |
| `core/agent.py` | маршрутизация, text-to-SQL, пересказ, графики, дашборды, контекст диалога | намерение определяют правила (`ROUTER_MODE=rules`), модель только по желанию; время и число вызовов модели возвращаются в `Result.timing` |
| `core/safety.py` | проверка SQL до выполнения | один оператор, только `SELECT`/`WITH`, чёрный список ключевых слов, служебные таблицы `_bi_*` и `information_schema` закрыты |
| `core/db.py` | доступ к PostgreSQL | запросы агента в `READ ONLY`, `statement_timeout` (`QUERY_TIMEOUT_MS`), `LIMIT` (`MAX_ROWS`); служебные таблицы дашбордов |
| `core/charts.py` | вид графика и его построение | допустимые типы: столбцы, линия, область, круговая, гистограмма, разброс, ящик; описание графика от модели проверяется на существующие колонки |
| `core/history.py` | чаты и сообщения | таблицы результатов не хранятся: храним SQL и пересчитываем при открытии чата, поэтому данные в старых чатах актуальны, а база не раздувается |
| `core/llm.py` | клиент модели | два провайдера (OpenAI-совместимый API и родной API Ollama); блоки `<think>` снимаются; при отказе сервера от `response_format` запрос повторяется без него; понятные ошибки вместо трассировок |
| `core/prompts.py` | все промпты в одном месте | |
| `core/analytics.py` | заготовка набора аналитических инструментов | есть поиск дубликатов (`find_duplicates`) с единым форматом результата `AnalysisResult` и регистр `TOOLS`, покрытые тестом; функция `analyze_unknown_csv` (статистика, аномалии, корреляции, сезонность, лаги по DataFrame) в приложении не вызывается. **К диалогу не подключено**: сценарии 3 и 7–9 выполняются через SQL от модели |

## 4. Потоки данных

### 4.1 Загрузка

CSV → определение кодировки и разделителя → разбор типов (числа, даты, десятичная запятая) → таблица в PostgreSQL → пересчёт профиля и схемы агента.
Малые файлы читает pandas, большие (от 50 МБ) идут куском за куском через `COPY`: память не растёт вместе с файлом, тип колонки при необходимости расширяется (число → текст), а не обнуляется.
Файл с тем же именем заменяет старую таблицу. Ошибка на середине загрузки откатывается целиком. Таблицу можно удалить из интерфейса.

### 4.2 Профиль данных («память о данных»)

Для каждой таблицы считаются размер, типы колонок, доли пропусков, топ-значения, период по колонке времени, число дубликатов; между таблицами ищутся связи по значениям. Из профиля собирается компактный текст схемы: он идёт в промпты модели и в сводку «Что передо мной?».

### 4.3 Вопрос → ответ

1. **Маршрутизация правилами** (`classify_request`): обзор данных, объяснение поля, запрос с вычислениями, «покажи иначе», дашборд, уточнение, отказ. Модель-маршрутизатор включается только при `ROUTER_MODE=llm`.
2. **Обзор** («Что передо мной?»): факты из профиля плюс описание от модели. Описание кешируется в рамках сессии (пока не обновлён профиль), повторный обзор модель не вызывает.
3. **Вычисляющий вопрос**: модель пишет SQL по схеме и истории диалога (`HISTORY_TURNS` реплик) → `safety` → выполнение. Если запрос упал, модель видит ошибку и исправляет его (до `SQL_RETRIES` раз). Если вопрос неоднозначен, модель отвечает `CLARIFY: …`, и агент задаёт пользователю уточнение.
4. **Ответ**: одиночные значения пересказываются шаблоном без модели, остальное объясняет модель простым языком, только числами из результата. SQL доступен под спойлером.
5. **График**: если пользователь назвал тип, берётся он; иначе правила подбирают вид по форме результата (дата + число → линия, категория + число → столбцы и т. д.). Модель выбирает вид только при `CHART_LLM=1`.
6. **«Покажи иначе»** (`rechart`): берётся последний результат диалога и строится другим видом, SQL не пересчитывается.

### 4.4 Дашборд

Запрос → модель возвращает набор виджетов (название и SQL) → каждый SQL проходит `safety` и считается **параллельно**, результаты кешируются на `DASHBOARD_CACHE_TTL` секунд → вид графика выбирается автоматически → дашборд сохраняется в `_bi_dashboards`.
Открывается из чата и со вкладки «Дашборды»; при открытии виджеты считаются заново (с учётом кеша на `DASHBOARD_CACHE_TTL` секунд), поэтому данные свежие. Дашборд можно удалить.

### 4.5 История и контекст

Каждая реплика пишется в `_bi_messages` (роль, текст, SQL, описание графика, id дашборда). При открытии старого чата таблицы пересчитываются по SQL, а агенту возвращается последний результат, поэтому «покажи то же самое иначе» работает и в старом диалоге. Если пересчитать нельзя (таблицу удалили), сообщение остаётся с пометкой.

## 5. Безопасность

| Угроза | Защита |
|---|---|
| модель сгенерировала изменяющий или опасный SQL | `safety.validate_sql`: один оператор, только `SELECT`/`WITH`, чёрный список ключевых слов |
| чтение чужих чатов или служебных данных | имена `_bi_*` и `information_schema` запрещены в SQL агента |
| тяжёлый запрос подвесил базу | `statement_timeout` и `LIMIT` на каждый запрос |
| случайная запись через запрос | транзакция `SET TRANSACTION READ ONLY` |
| удаление таблицы из интерфейса | разрешено только для загруженных таблиц, имя проверяется по списку и экранируется |
| утечка ключей | настройки через переменные окружения, `.env` в `.gitignore` |

## 6. Работа со слабыми моделями

- Правила вместо модели там, где это возможно (маршрутизация, тип графика, простые вопросы, пересказ одиночных значений).
- Самоисправление SQL: ошибка базы возвращается модели.
- Устойчивый разбор ответов: блоки `<think>` и обрамление ```` ```sql ```` снимаются, JSON достаётся из текста.
- Короткая история диалога и компактная схема, чтобы уложиться в контекст 7B-модели.
- Честные отказы: на неоднозначные или недопустимые запросы агент уточняет или отклоняет, а не выдумывает.

## 7. Скорость

| Мера | Эффект |
|---|---|
| маршрутизация правилами | минус один вызов модели на каждый вопрос |
| шаблонный пересказ одиночных значений | минус один вызов модели |
| кеш описания данных в рамках сессии | повторный «Что передо мной?» без модели |

## 9. Развёртывание и сеть

`docker-compose.yml` запускает три сервиса в одной сети:

| Сервис | Образ | Порт | Данные |
|---|---|---|---|
| `db` | `postgres:16` | 5432 | том `pgdata` |
| `ollama-gpu` / `ollama-cpu` (профили) | `ollama/ollama` | 11434 | том `ollama` (модели) |
| `app` | собирается из `Dockerfile` (Python 3.14, uv) | 8501 | код монтируется из репозитория |

Приложение обращается к модели по имени `ollama`, его носят оба профиля, поэтому переключать адрес не нужно.

**К каким внешним адресам нужен доступ.** Только при установке и первом запуске; в работе платформа в интернет не ходит, кроме сервера модели, если вы указали внешний `LLM_BASE_URL`.
Список составлен по `Dockerfile`, `docker-compose.yml` и `pyproject.toml`.

| Когда | Адрес | Зачем |
|---|---|---|
| сборка и запуск | `registry-1.docker.io` (Docker Hub) | образы `postgres:16`, `ollama/ollama`, `python:3.14-slim` |
| сборка | `ghcr.io` (GitHub Container Registry) | образ `uv` (`ghcr.io/astral-sh/uv`) |
| сборка | `deb.debian.org` | пакет `build-essential` для сборки зависимостей |
| сборка | `pypi.org`, `files.pythonhosted.org` | Python-зависимости (`uv sync`) |
| первый запуск | `registry.ollama.ai` | скачивание весов модели (`ollama pull`) |
| работа, если выбран внешний сервер модели | адрес из `LLM_BASE_URL` | запросы к модели |

Реестры могут перенаправлять скачивание на свои CDN-адреса (хранилища слоёв образов и весов): при ограничении сети по списку доменов добавьте и их, их показывает ошибка при загрузке.
Для работы совсем без интернета образы и модель заранее загружают на машине с доступом и переносят (`docker save`/`docker load`, том `ollama`).
Поисковые системы не используются нигде.

## 10. «Идеальная» архитектура (не реализовано)

Что мы добавили бы, будь у нас больше времени. Это план, а не описание текущей версии.

```
 Браузер ──► Веб-интерфейс ──► API-сервер (FastAPI) ──► Очередь задач (долгие запросы, прогресс, отмена)
                                    │                         │
                  ┌─────────────────┼─────────────────────────┤
                  ▼                 ▼                         ▼
          Семантический слой   Оркестратор агента     Аналитические инструменты на Python
          (описания колонок,   (роутер малой моделью, (сезонность, корреляции и лаги,
           метрики, словарь)    SQL-модель, модель-    сегментация, прогноз;
                  │             рассказчик)             считает код, модель только объясняет)
                  │                 │                         │
                  └────────┬────────┴──────────┬──────────────┘
                           ▼                   ▼
                  Драйверы БД: PostgreSQL · ClickHouse     Кеш (Redis): профиль, обзор, результаты
                           │
                  Метаданные: чаты по пользователям, дашборды, «золотой набор» вопросов
                  Наблюдаемость: время этапов, ошибки SQL, оценка точности в CI
```

| Улучшение | Зачем |
|---|---|
| ClickHouse как второй драйвер | требование кейса, быстрые агрегаты на больших таблицах |
| Семантический слой: модель один раз описывает смысл каждой колонки при загрузке | точнее SQL и ответы про поля, меньше промпт |
| Аналитические инструменты на Python для сценариев 7–10 | сезонность, лаги, корреляции и прогноз считает код, а не модель: меньше галлюцинаций |
| Разные модели под разные задачи (малая для маршрутизации и SQL, большая для пересказа) | скорость и качество на ограниченном железе |
| Потоковый вывод ответа и статус по этапам | пользователь видит ход работы, а не ждёт |
| Очередь задач и отмена долгих запросов | интерфейс не блокируется на минутных дашбордах |
| Пользователи и привязка чатов к ним | сейчас история общая |
| Редактирование дашбордов в чате («добавь виджет», «убери») | сейчас дашборд создаётся целиком |
| Кеш профиля и обзора данных, общий для сессий и переживающий перезапуск (Redis или таблица в БД) | сейчас описание данных кешируется только внутри сессии, и каждая новая сессия снова ждёт модель |
| Ответы без модели на простые вопросы (число строк, список таблиц и колонок) из профиля и `COUNT(*)` | на слабой видеокарте простой вопрос занимает около 10 секунд, а мог бы выполняться мгновенно |
| «Золотой набор» вопросов и автоматическая оценка точности SQL в CI | измеримое качество, защита от регрессий при смене модели |

## 11. Ограничения текущей версии

- Только PostgreSQL, схема `public`.
- Кеши хранятся в памяти приложения и не переживают перезапуск; кеш описания данных живёт в рамках сессии.
- История чатов общая для всех пользователей.
- Точность на сложных запросах зависит от размера модели; на 7B возможны ошибки, которые самоисправление исправляет не всегда.
- Сложные аналитические сценарии (лаги, корреляции, прогноз) полностью зависят от SQL, который напишет модель.
